## 一页纸看懂

**把 xay 想成一家公司：**

| 公司里的东西 | 在 V2 里是什么 | 和现在的区别 |
|---|---|---|
| **员工**（Codex 1、Gemini 2……） | **归某个项目**的长期 AI。名字、工作笔记、桌子永远保留，换一个 Claude 对话它也还在 | 现在派一次活就开一个新对话，做完就散 |
| **桌子** | 每个员工一个固定的独立工作区（git worktree）。每件活做完单独合并回项目，桌子留着接着用 | 现在每件活建一个工作区，失败了直接删，成果跟着丢 |
| **原生对话** | 员工在 Codex、dsh、agy 里的那个对话。相似的活在同一个对话里接着做 | 现在每次都是冷启动 |
| **记忆条** | 对话已经用了多少上下文（比如 62%）。快满时管家安排"整理记忆"（压缩） | 现在看不到，满了就失忆 |
| **账本** | 一个数据库文件，按顺序记下所有事 | 现在散在 7 种文件里，页面只能靠猜 |
| **管家** | 常驻的小程序：排活、选人、管记忆、催进度、送信、管预算 | 现在是五个各管一摊的小循环 |
| **监控屏** | 公司页和看板只照账本画；点开一个员工，能看到他此刻在想什么、在做什么、记忆用了多少 | 现在真实页面常是空的，还会偷偷显示示例数据 |

**六条铁规矩：**
1. **只有一本账**：页面和命令都只读账本，不靠猜。
2. **员工长期在岗**：相似的活交给同一个员工，在原对话、同一张桌子上接着做；只有需要同时干几件事、或者换一种 AI 时才招新人。
3. **记忆有人管**：
   - 门槛：每家 AI 的压缩门槛不同（Codex 60%、dsh 55% 或 30 万 token、agy 50% 或者已经做了 3 轮，谁先到算谁），避开它们自己的自动压缩。（M3 实测后修订，见 §3.2 表下的说明）
   - 怎么压：优先用该 AI 自带的压缩；没有或者不好用，就照 Claude Code 的做法——让员工写一份固定格式的交接摘要，再带着摘要开新对话。
   - 压完检查：压缩后员工要先复述"我在做什么、改过哪些文件、下一步是什么"，复述不出来就提醒负责人。
4. **看得见脑子**：思考、动作、记忆条实时显示在页面上；哪家不提供某项信息，就写"这家看不到"。
5. **成果不丢**：桌子上的东西只有在你同意解雇这个员工时才会删；失败、暂停、超时一律保留。
6. **有刹车**：
   - 每个员工、每件活都有 token、时长、轮数三条预算线；
   - 页面上有一个红色"全部停下"按钮；
   - 只有你自己这台电脑能操作，别人连不进来。

**怎么做**：只用 Python 自带的库，加一个 SQLite 数据库文件；网页外观保留，只换掉数据来源。代码全部放在 `V2/`，端口用 **7879**，命令叫 `xay2`，旧系统照常用。第一个里程碑做完，你就能在新公司页上看到真实数据（§6）。

## 1. 为什么要从底层重构（现在的毛病）
- **编号对不上**：同一次派活有 `ls_…` 和 Claude 对话号两个编号，几个命令各按自己那个去查；公司页的刷新信号只盯着 `org/default`，所以真实页面几乎不刷新。取不到数据时，页面会悄悄显示示例数据（`xay-org.html:1610`）。
- **状态靠猜**：员工忙不忙，是看某个文件在不在、多久没动静猜出来的；"计划"其实就是最近 60 次派活的记录；系统里根本没有"做到第几步"这个信息。`meta.json` 有 3 个程序在写，还会被整份覆盖。
- **丢成果**：`xay-run:410-411` 只要状态不是 done 就删工作区；暂停的任务等满 1800 秒也会被删。
- **员工是一次性的**：agy 第一轮结束就关掉输入，下一轮只能冷启动续接，经常 20 秒就失败；没人看着上下文用了多少。
- **监控没接上，驱动有隐患**：
  - 看门狗没有接进来；
  - agy 的额度报错识别不到；
  - "一直报错、不调用任何工具"的死循环抓不到（那一次烧掉约 94 万 token）；
  - Codex 续接时会悄悄改走中转站（`codex_appserver.py:310-322`）；
  - 降级到 exec 方式后会卡死；
  - agy 的 `--add-dir` 被忽略了。

## 2. V2 长什么样：四层
```
┌──── 监控屏（网页，只开在本机 127.0.0.1:7879）────┐  公司页（部门房间、工位、写信动画、信件栏、计划版本）
│  读"快照" + 实时推送；员工透视窗读"直播通道"     │  员工透视窗：在想什么 / 在做什么 / 记忆条 / 工作笔记
└──────────────────────▲──────────────────────────┘
┌──── 管家（常驻 1 个）────────────────────────────┐  排活 · 选人 · 管记忆 · 规则监工 · 送信 · 预算和总闸
│  它是唯一做决定的地方；重启后从账本恢复           │  每 10 秒检查各工位的心跳
└──────────────────────▲──────────────────────────┘
┌──── 账本（~/.xay/v2/xay.db，一个 SQLite 文件）───┐  只追加的事件 + 从事件算出来的现状表
└──────────────────────▲──────────────────────────┘
┌──── 工位（独立的小程序，管家挂了也不受影响）──────┐  Codex：每条额度线路一个共享的 app-server，里面装着所有 Codex 员工
│  适配器把各家输出翻译成统一事件                    │  agy：每个员工一个进程（最多 2 个）· dsh：每一轮临时起一个进程
└───────────────────────────────────────────────────┘
负责人（任何 AI）用 xay2 命令：组部门、写计划、派活；等结果只用 xay2 wait 和 xay2 brief，回复很短
```
- 工位用"脱离父进程"的方式启动，自己直接管着 AI 的命令行。所以管家重启时，正在跑的活不会中断。
- 工位每 10 秒报一次平安。没报的，管家标成"离线（崩溃）"，然后用原生续接把它接回来；接不回来就标"需要你"。

## 3. 核心设计

### 3.1 员工：三层常驻、一张桌子、怎么选人

**① "常驻"分三层**：身份永远在，对话尽量接着用，进程只是为了快、可以随时关掉

| | 身份（永久） | 对话（尽量接着用） | 进程（可以关掉） | 下班和接回 |
|---|---|---|---|---|
| Codex | 名字、笔记、桌子 | 一个 thread：用 `turn/start` 接着做，忙的时候来活就用 `thread/queue/add` 排队；换额度线路时带着原来的线路设置重新 `thread/resume` | 每条线路一个共享的 app-server（Plus 一个、中转站一个） | 空闲 15 分钟就 `thread/unsubscribe`；来活了再 `thread/resume` |
| dsh | 同上 | `--session-id`（对话由 dsh 自己保存） | 每一轮起一个进程 | 不需要 |
| agy | 同上 | 热续：同一个进程，在输入里一行写一件活；冷续：`--conversation` | 每个员工一个进程，最多 2 个同时开，空闲 10 分钟就关 | 冷续后 30 秒内既没调用工具也没输出文字，就判为续接失败，自动走交接压缩、开新对话（记一条"第 N 段记忆，原因：续接失败"） |

**② 每个员工一张桌子**（工作区跟着员工走，每件活单独合并回项目）
- 为什么这么做：dsh 和 agy 的对话记住的是"在哪个目录干活"，换一个目录就等于换了记忆；同一张桌子还能直接用上次的编译缓存。
- 流程（所有 git 操作都由工位来做，执行者自己仍然不 commit、不 push）：
  1. **招聘**：建 `~/.xay/v2/desks/<项目>/<员工>`，分支 `xay/emp/<员工>`。
  2. **开工前对齐**：给主项目当前状态拍一张快照（包括还没提交的改动，沿用 `git stash create`）。
     - 桌子上没有没合并的东西（平常都是这样）→ 直接把桌子对齐到这张快照。目录不变，没被 git 管的编译缓存也留着，不会有冲突。
     - 桌子上有"保留下来、还没合并"的改动 → 先标"需要你"，由负责人决定合并还是丢掉，然后再开工。
     - 记下这件活开始时桌子的版本。
  3. **合并回项目**：把"这件活开始时 → 现在"的改动搬回主项目（沿用现有的补丁 + 三方合并逻辑）；合并成功后在桌子上打一个标记。桌子既不删除也不重置。
  4. **删桌子**：只有在解雇这个员工、而且你点头的时候。
- 并行：两个员工各用各的桌子。两件活要改的文件有重叠时，开工前就提醒。想要"同一个人的经验 + 同时干两件"，Codex 可以用 `thread/fork` 复制出一个新员工，配一张新桌子。
- 只读的活（比如审查）：桌子同步之后直接在上面跑，不另开工作区。

**③ 选人：三步规则**（不靠打分）
1. **先排除不合适的**：
   - 只看同一种 AI；
   - 最近连续失败 2 次的不选；
   - 记忆条超过 80% 而且压缩不了的不选；
   - 负责人写了 `--to Codex1` 就直接交给他。
2. **优先让老员工接着干**：满足下面任一条，就交给这个员工；他正忙就排进他的队列。
   - 这件活依赖的前一件是他做的；
   - 要改的文件和他最近 3 件活有重叠；
   - 他是同一个部门的。
3. **招新人**：
   - 没有满足第 2 步的员工；
   - 或者那个员工正忙，这件活已经可以开工，预计要等 10 分钟以上，而且还有空名额。
- 每次分配都写明理由，页面会显示，比如"交给 Codex 1：上一件活改过同一批文件"。

### 3.2 记忆管理（核心）

**① 记忆条怎么算**（Fable 在本机样例数据上核实过）

| AI | 当前上下文 | 窗口大小 | 更新频率 | 注意 |
|---|---|---|---|---|
| Codex | `tokenUsage.last` 这一轮的 token（**不能用 `total`，那是累计值，会超过 100%**） | `modelContextWindow`；为空时查提供者表 | 实时 | 压缩后要到下一轮才准，页面先显示"等校准" |
| dsh | 最近一步 `step_end.usage.totalTokens`（**不能只看 inputTokens，它不含缓存，会少算约 4 倍**） | 每次开工前从 `dsh --dump-config` 读出当前路由的模型窗口，不写死（本机路由是 262,144） | 每一步 | 两步之间掉了 10% 以上、而且掉之前已经用到 40% 以上，就判定 dsh 自己压缩了一次，记一笔（M3 按本机 70 次真实压缩日志改的，原来的"掉 30%"会漏掉一半多） |
| agy | 最近一步的新输入 **加上缓存读取**（agy 报的 input_tokens 不含缓存） | 256,000（M3 核实；原来表里的 104.9 万是错的） | 每一步 | 思考内容看不到 |

记忆条只在变化 ≥2% 或者距上次 ≥30 秒时写进账本；直播通道里是实时的。

**② 什么时候压缩、怎么压缩**（三家门槛错开，避免和它们自己的自动压缩撞车，压两次）

| | 两件活之间 | 干活中途 | 它自己的自动压缩 |
|---|---|---|---|
| Codex | ≥60% → 用自带的 `thread/compact/start` | 交给 Codex 自己的自动压缩（不打断） | 照常让它压，只记一笔；2 小时内自动压缩了 2 次及以上，下一件活前改用交接压缩 |
| dsh | ≥55% 或 ≥30 万 token → 交接压缩（headless 下 `/compact` 会被当成普通文字） | 交给 dsh 自己（M3 实测：它在窗口的 75% 左右自动压，本机约 19.6 万）；如果报"上下文超限"，就强制交接压缩 | 根据记忆条突降判断出来，记一笔 |
| agy | ≥50% **或者**已经做了 3 轮 → 先用自带 `/compact`（M3 实测 65,211 → 16,889，压完还记得），不行再交接；同一段记忆自带压缩满 2 次就改走交接、开新对话 | ≥70% 时，这一轮结束后马上交接；连续 3 次报错、中间没用过任何工具 → 停下，然后交接 | 不靠它 |

**③ 交接压缩**（照 Claude Code 的压缩方式）
- **员工自己写**交接摘要（不超过 120 行，固定七节）：
  1. 目标
  2. 已经定下来的事
  3. 改过的文件（写到关键的"文件:行"）
  4. 验收命令和最近一次的结果
  5. 踩过的坑和解决办法
  6. 还没做完的和下一步
  7. **不要重复做的事**
- 员工写不出来时（比如卡在死循环、上下文已经超了），工位用账本、`git diff --stat`、上一份汇报自动拼一份"机器版"摘要。
- **新对话的第一轮**：先给它看工作笔记、`.xay/context.md` 和任务卡（Codex 用 `additionalContext` 传进去，不混进任务卡），然后要求它用 3 行复述"我在做什么、改过哪些文件、下一步"。
  - 工位自动检查复述里有没有提到当前任务和至少一个改过的文件名。
  - 没提到就标"可能失忆"，提醒负责人。

**④ 工作笔记 = 员工的长期记忆**
- 平时用的部分不超过 1500 token，更早的内容归档进账本。
- 每件活结束时自动追加一段，每次压缩时重新整理一遍。
- Codex 自带的 `thread/memory/read` 读出来的摘要也合并进来。
- 页面可以直接看。

### 3.3 实时监控：看得见每个员工的"脑子"

**① 每家能看到什么**（实话实说）

| | 思考 | 动作 | 回复 | 记忆条 | 计划步骤 | 状态 |
|---|---|---|---|---|---|---|
| Codex | ✓ 逐字的思考摘要（`item/reasoning/summaryTextDelta`） | ✓ 实时，带命令输出 | ✓ 逐字 | ✓ 实时 | ✓ 自带（`turn/plan/updated`） | ✓ 自带（空闲 / 干活 / 等审批 / 未加载 / 出错） |
| dsh | ✓（`thinking` 事件） | ✓ | ✓ | ✓ 每一步 | 从回复里的标记读 | 从事件推出 |
| agy | ✗ 看不到（样例里思考 token 是 0） | ✓ | ✓ | ✓ 每一步 | 从回复里的标记读 | 从事件推出 |

**② 两条通道**
- **直播通道**：逐字的思考、输出、命令结果。只保留最近一段记忆，压缩存放 7 天，经过脱敏，不写进账本。
- **账本**：只记里程碑——开工、第 2 步、整理记忆、写信、做完。

**③ 页面上怎么看**
- **公司页工位**：头顶有个思考小气泡（显示最近一句），显示器下面有记忆条和"第 2 步 / 共 4 步"。整理记忆时角色换成"整理中"的动作。
- **员工透视窗**：点工位打开，从看板现有的消息流改出来。
  - 上面依次是：正在想 / 正在做 / 记忆（用量、第几段、笔记） / 这段记忆里做过的活。
  - 最下面一行输入框可以插话：Codex 当场能收到，其他 AI 等这一轮结束后才收到。

**④ 规则监工盯着这些数据**（只用固定规则，不靠 AI 自己评价自己）
- 一直在想却半天没有动作；
- 连续报错、中间不用工具；
- 记忆条涨得太快；
- 很久没有任何输出。
- 发现了先提醒，再按附录 B 的反应表处理。

### 3.4 一本账：编号、计划、进度、成果
- **编号**：
  - 项目 `ws`；员工归项目。
  - 对话 `conv`：Claude 对话号、Codex thread 号、旧的 `ls_` 都对到同一个 `conv`。
  - 任务和信件都记在某个 `conv` 下面。
  - 公司页按项目显示，可以按对话筛选。
- **计划是一等对象**（你最开始提的根本问题之一，放在核心功能里）：
  - 每件事都写清：交给谁、依赖哪件、要改哪些文件。
  - 总经理直接改，每改一次版本号 +1，并写明原因。
  - 别人提"改计划申请"，负责人同意后自动生成新版本。
  - 页面能看到"第 3 版：把算运费改给页面部，原因：……"。
- **进度三条来源**：
  - Codex 自带的计划步骤；
  - 回复里的标记 `【进度 2/4】写测试`；
  - 员工跑 `xay2 progress`，写进桌子里的发件箱。工位只认属于自己任务的记录，限制大小，先检查格式再记账。
- **结论看证据**：
  - 证据包括：这一轮的状态、汇报里怎么说、实际改了什么、验收命令的结果。
  - 证据对得上 → 合并回项目，等负责人验收。
  - 证据对不上（比如汇报说"做完了"，状态却是失败）→ 标"需要你"。桌子一律保留。

### 3.5 刹车与安全
- **预算**：
  - 每个员工、每件活都有 token、分钟、轮数三条线。Codex 用自带的 `thread/goal/set{tokenBudget}`，其他 AI 由工位自己计数。
  - 用到 70% 提醒；90% 让它收尾；100% 直接打断。
  - agy 每天最多 40 次调用的限制保留。
- **总闸**：`xay2 stop --all` 或页面上的红色按钮。依次尝试：先请它停 → 再强制结束进程 → 再直接杀掉。任务标为"已停下"，桌子全部保留。
- **控制安全**：
  - 网页只开在本机 127.0.0.1。
  - 写操作要带专用请求头，还要检查来源。
  - 命令行通过只有你自己能读写的本机通道发指令。
  - 执行者不能使用控制命令。
- **崩溃恢复**：管家启动时检查三件事：
  - 没有心跳的员工 → 标"离线"；
  - 开了工没收工的活 → 标"被打断"，桌子保留；Codex 先尝试 `thread/resume` 接回，其他 AI 标"需要你"。
- **账本维护**：
  - 账本有版本号，每条事件也带版本号，遇到不认识的事件类型就跳过；
  - 升级脚本放在 `V2/xay/core/migrations/`；
  - 每天自动备份一份（`VACUUM INTO`）；
  - `~/.xay` 不要放进 iCloud 同步目录。

## 4. 技术选型

| 决定 | 选择 | 理由 | 没选 |
|---|---|---|---|
| 语言 | Python 3.11，只用自带库 | 已经在真实 CLI 上跑通的驱动、额度、合并代码可以直接移植；执行者最熟 Python；不用安装任何东西 | TypeScript：要重写已验证的代码，而问题本来就不出在语言上。Go/Rust：要编译，以后不好维护 |
| 存储 | 一个 SQLite 文件（WAL 模式）：只追加的事件表，加上同一事务里算出的现状表；`xay2 rebuild` 可以从头重算一遍 | 多个进程同时写也安全；查询简单；hcom 和 mcp_agent_mail 也是这么做的 | 每个对话一个 jsonl 文件（第九版草案）：同时写要自己加锁、自己合并，最后又会回到靠猜 |
| 进程 | 1 个管家 + 独立的工位 + 很薄的命令行 | 做决定的地方只有一个；工位让对话和桌子能常驻；管家挂了不影响正在干的活 | 每件活起一个进程（现在的做法）：没法常驻，也没法接着干 |
| 适配层 | 按 ACP 的语义统一成这些动作：开始、续接、发一轮、插话、取消、事件流、**压缩、记忆用量、预算**；能做什么按"能力"判断；模型限制、窗口大小、门槛都写在提供者表 `providers.py` 里，启动时检测各 CLI 的版本 | 加一家新 AI 只需要加一个适配器；CLI 升级（agy 已经从 1.4.9 变成 1.4.11）能被及时发现 | 读终端画面（tmux 那一派）：靠猜 |
| 页面 | 原生 JS 拆成模块，不需要打包；快照 + 实时推送 + 直播通道；示例模式 = 用示例账本回放，和真实数据走同一套代码 | 保留现在的外观；示例数据和真实数据不会对不上 | React 之类：要打包，还要重写页面 |
| 负责人怎么等结果 | `xay2 wait --conv X --since <seq> --timeout 240` 只返回需要处理的事（需要你 / 已汇报 / 已合并 / 提醒 / 改计划申请），每条不超过 2 行；`xay2 brief` 不超过 25 行 | 负责人花的 token 最贵，所以只给它看要紧的 | 让负责人去读 JSON 快照或日志 |

## 附录 A：账本事件（节选）
| 事件 | 谁写 |
|---|---|
| `conv.begun`、`dept.opened/closed` | 总经理 |
| `employee.hired {ws, label, agent}`、`employee.session {native_id, segment, reason}`、`employee.online/offline {reason}`、`station.heartbeat` | 管家 / 工位 |
| `desk.synced/conflict`、`task.landed/kept`、`desk.removed`（只在你点头后） | 工位 / 管家 |
| `task.added/changed/removed/assigned {plan_version, reason}`、`proposal.made/decided` | 总经理直接改；其他人走申请 |
| `turn.started/ended {evidence}`、`task.progress {step, of, text}`、`task.reported {claim, summary}` | 工位（执行者的回报先经工位检查） |
| `context.updated {used, window, pct}`、`context.compacted {method: native/native_auto/handoff/machine, before, after}`、`recall.checked {ok}`、`notes.updated` | 工位 / 管家 |
| `budget.warned/stopped`、`letter.*`、`decision.opened/resolved`、`signal.*`、`control.*` | 按规则写 |

- 任务状态：`planned → ready → queued → working ⇄ needs_you → reported → done | failed | canceled`（参照 A2A）。
- 员工状态：`working / queued / blocked / idle / compacting / offline / failed`，由事件算出来，不靠猜。

## 附录 E：和 Fable 5.1 的协作记录
- 采纳的建议：
  - 员工归项目；
  - "常驻"分三层；
  - 一个员工一张桌子、每件活单独合并回项目；
  - 选人用三步规则；
  - 记忆条的算法（Codex 用 `last`，dsh 用 `totalTokens`）；
  - 三家的压缩门槛错开；
  - 机器版交接摘要和压缩后的复述检查；
  - 工位独立运行 + 心跳；
  - 探针日；
  - 第一个里程碑先做真页面；
  - 预算、总闸、控制安全；
  - `wait` 只返回要紧的事、`brief` 有长度上限；
  - 账本版本号和每日备份。
- 我保留的不同意见：
  - **计划版本和改计划申请仍然放在核心功能里（M4）**，没有像 Fable 建议的那样往后推。理由：你一开始的任务说明里就把"计划不能改、没有修改记录"列为 V2 必须解决的根本问题。
  - Codex 的 app-server 改成"每条额度线路一个"，而不是全部共用一个。理由：Plus 和中转站在进程层面配置的线路不一样，分开可以避免混用；而且"机密项目只走 Plus"这条规则更容易守住。
